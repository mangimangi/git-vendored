# git-vendored: test coverage is measured for every shipped script and enforced at 99%

> Unit 6 of plan `git-dev-883c` (record: `mangimangi/git-dev`, `.pearls/docs/epics/git-dev-883c.md`). Added to the plan by the owner on 2026-11-28. Delivers into `plan/git-dev-883c`. Re-check every figure and code reference against the code before using it.

## Problem

The owner, 2026-11-28: "we need 99 test coverage for all of these tool repos using bats or pytest right? these are core tooling and they need to be safe and not regress".

git-vendored's scripts are copied into every repository that vendors a tool, and `check` is what guards vendor-protected files there. Today nothing measures how much of them the tests exercise, and nothing fails when coverage drops:

- `ci/test.sh` runs `python -m pytest tests/ -v` with no coverage; `pyproject.toml` has no `[tool.coverage]` section; `ci/setup.sh` does not install a coverage tool.
- Measured by the planning session on `main` (2026-11-28, `pytest --cov=.` in-process, 426 tests passing): `templates/install` 92% of 762 statements, `templates/check` 63% of 153, `templates/remove` 93% of 148, `templates/feedback` 94% of 96, `validate` 96% of 201, `templates/audit` 98% of 111. A script the tests start as a subprocess is not counted by that run, so some of these understate what the tests reach; nothing says which.
- The shell scripts are not measured at all: `install.sh`, `templates/lib/vendor-helpers.sh`, and the job scripts under `ci/`.

A later unit of this plan (unit 5) changes `templates/check`, `templates/install` and `validate`. This unit puts the safety net under them first.

## What already was decided (do not reopen)

- The threshold is 99% line coverage, enforced: the `test` job fails below it.
- It applies to the Python scripts the repository ships (`templates/install`, `templates/check`, `templates/remove`, `templates/audit`, `templates/feedback`, `validate`). Vendored copies of other tools (`.vendored/pkg/**`) and the tests themselves are not part of the measure.
- Shell scripts get bats tests for each behaviour, run by the `test` job, with no numeric threshold (agreed 2026-11-28: no shell coverage tool is required; pytest measures the Python).
- Gaps are closed with real tests. A line is excluded from the measure only when it cannot be reached by a test, with a comment on the line saying why; exclusions are not a way to reach the number.
- The checks run through git-cicd (`.vendored/configs/git-cicd.json`, job `test`: `ci/setup.sh`, `ci/test.sh`), on the Python floor the repository declares; no Python version is written in a workflow.
- No vendor-protected file is added, changed or deleted (`.vendored/` files a manifest lists, and the workflows vendors install). Run `python3 .vendored/check --base origin/plan/git-dev-883c` before finishing.

## What ships

- Coverage is measured honestly for every shipped Python script
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `pyproject.toml` (`[tool.coverage.run]`, `[tool.coverage.report]`), `ci/setup.sh`, `ci/test.sh`, `tests/conftest.py`, `AGENTS.md`, `README.md`
  - shape: The `test` job measures line coverage of the six shipped Python scripts by name (they have no `.py` extension), and of nothing else. Runs of a script that a test starts as a subprocess are counted, so the figure is what the tests really execute. The job prints the per-file report with the missing lines. `ci/setup.sh` installs what that needs; a local `git-cicd check` gives the same figure as CI. The docs say how to read the report. No threshold yet in this issue if the measured figure is below it: this issue ends with a true number in the pull request description for each file.

- The gaps are closed to 99% in every shipped Python script
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `tests/` (new and extended test files), and the shipped scripts only where a line is provably unreachable or a defect is found
  - shape: Tests are added until each of `templates/install`, `templates/check`, `templates/remove`, `templates/audit`, `templates/feedback` and `validate` is at 99% or more, starting with `templates/check` (63% measured). The tests exercise behaviour a consumer relies on (what is protected, what an install branch may change, what an install writes and to where, what a removal leaves, error paths with their messages and exit codes), not lines for their own sake. Network and `gh` calls are replaced at the boundary the existing tests already use. A defect a new test exposes is fixed in the script with the test that shows it, and named in the pull request; a behaviour change beyond a defect fix is out of scope.

- The threshold is enforced
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `pyproject.toml` (`fail_under`), `ci/test.sh`, `AGENTS.md`, `README.md`
  - shape: The `test` job fails when total coverage of the shipped Python scripts, or of any one of them, is below 99%, with the report showing which file and lines. The docs state the rule: a change that lowers coverage below 99% fails the verdict, and adds its tests in the same pull request.

- The shell scripts have bats tests
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `tests/` (bats files), `ci/setup.sh`, `ci/test.sh`, `.vendored/configs/git-cicd.json` (`paths` of the `test` job), `AGENTS.md`
  - shape: `install.sh`, `templates/lib/vendor-helpers.sh` and the scripts under `ci/` each have bats tests covering every behaviour they have: each branch of a decision, each error message and exit code, what is written where. They run in the `test` job (setup installs bats; no network in the tests) and locally through `git-cicd check`. Where existing pytest tests already drive a shell script end to end they may stay; the bats tests cover what those do not. A failing bats test fails the job.

## Acceptance criteria

- `.vendored/pkg/git-cicd/git-cicd check --setup` passes in a clean checkout and prints a coverage report listing the six shipped Python scripts, each at 99% or more.
- Lowering coverage (for example removing one test file) makes the `test` job and the verdict fail, shown once in the pull request description.
- Subprocess runs are counted: shown by a script whose tests only start it as a subprocess appearing in the report with a non-zero figure.
- Every exclusion from the measure carries a comment with its reason; the pull request lists them.
- The bats tests run in the `test` job and cover `install.sh`, `templates/lib/vendor-helpers.sh` and each `ci/` script.
- The pull request into `plan/git-dev-883c` has a passing `Verdict / git-cicd:verdict`.
- `python3 .vendored/check --base origin/plan/git-dev-883c` reports nothing.

## Out of scope

- Any behaviour change to the shipped scripts beyond fixing a defect a new test exposes (unit 5 changes `check`, `install` and `validate`).
- A coverage figure for shell scripts.
- Raising or changing the declared Python floor.
- Vendor-protected files; anything in git-cicd or git-semver.
