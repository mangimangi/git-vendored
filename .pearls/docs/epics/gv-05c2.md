# git-vendored: check, update and validate are jobs; an install leaves a repository consistent

> Unit 5 of plan `git-dev-883c` (record: `mangimangi/git-dev`, `.pearls/docs/epics/git-dev-883c.md`). Agreed with the owner on 2026-11-28, and extended the same day with requests from a consumer (`mangimangi/git-dev`, `.pearls/docs/consumer-note-git-cicd-v0.0.3-and-v0.0.4-in-medici.md`), which the owner added to the plan. Delivers into `plan/git-dev-883c`. Re-check every code reference against the code before using it.

## Problem

Two things.

**git-vendored's own repository still runs hand-written workflows.** git-cicd v0.0.4 and git-semver v0.0.16 are installed here (#124, #127), and the pull request checks already run through git-cicd (`test`, `vendor-check`), with coverage held at 99% (#125). What is left outside it:

| Workflow | Trigger | What it runs |
|---|---|---|
| `version-bump.yml` ("Bump & Release") | push to `main`; manual with `bump_type`, `subdirectory`, `changelog_description` | `python3 .vendored/pkg/git-semver/release bump` / `publish`, chosen by the head commit's message |
| `install-vendored.yml` ("Install Vendored") | cron `0 9 * * 1`; manual with `vendor`, `version`, `private`; callable | `python3 .vendored/install "$VENDOR" --version "$VERSION" --pr --deps=install $PRIVATE_FLAG`, with `${{ inputs.vendor }}` written straight into the script |
| `validate-vendor.yml` ("Validate Vendor") | manual with `repo`, `version` | `python3 validate "$VALIDATE_REPO" --version "$VALIDATE_VERSION"` |
| `check-vendor.yml` ("Check Vendor Files") | every pull request | `python3 .vendored/check`; already duplicated by the `vendor-check` job |
| `dogfood.yml` | after "Bump & Release" | git-dogfood, retired |

**An install does not leave a consumer consistent.** Seen in medici and in the git- tools' own repositories on 2026-11-27/28:

- git-vendored writes a vendor's registry (`.vendored/manifests/<vendor>.registry`: `repo`, `install_branch`, `protected`, `allowed`) once, when the vendor is first added (`save_vendor_config`, `templates/install` line 120). On an upgrade it is not refreshed. medici registered git-cicd at v0.0.2, so its registry still allows only `.github/workflows/git-cicd.yml`, a file later versions delete; a session that ran `git-cicd generate` as the tool instructs was rejected by `.vendored/check` ("Protected vendor files were modified: .github/workflows/git-cicd-open.yml").
- An install pull request never carries workflow files: after staging, `templates/install` unstages `.github/workflows/` (lines 1061-1068), because the workflow's own token may not push workflow files. So after an upgrade of a tool whose workflows changed, the tool is on `main` and its workflows are not; the manifest lists files the pull request did not deliver. The same is true of this repository's `main` today.
- The update form and the add form of the vendor argument look alike. `mangimangi/git-cicd` means "add a new vendor" and fails with `Vendor 'git-cicd' is already registered` when it is; the update form is `git-cicd`. A trailing space (`mangimangi/git-cicd `) fails with `Cannot access repo`, which points at the token.
- `python3 .vendored/check --base <ref>` prints "No changed files" when the only changes are staged or uncommitted: it reads commits only, and does not say so (`--staged` exists, lines 235 and 249).
- `check` takes the source branch from `GITHUB_HEAD_REF` (`get_branch_name`, `templates/check` lines 129-131); git-cicd gives a script `CICD_SOURCE_BRANCH`. This repository's `ci/vendor-check.sh` copies one into the other; every repository that runs the check as a git-cicd step would need the same wrapper.

## What already was decided (do not reopen)

- Generated files belong to the repository: it generates and commits them, and they are allowed, never protected (the owner accepted this request). git-cicd will stop listing them in its manifest (a separate issue in git-cicd). git-vendored's part is that the registry a vendor ships is what the check uses after every install.
- An install pull request carries workflow files when it is pushed with a token that may write them. The owner expects each repository to have a `VENDOR_PAT` with that permission. With only the workflow's own token nothing changes: workflow files are left out, and the pull request says so.
- The Monday update is kept like-for-like as a `cron` job (owner: "id say keep it just to test the cron trigger").
- What `install.sh` installs into a consumer does not change in this unit: `check-vendor.yml` and `install-vendored.yml` still ship.
- git-vendored's own `.vendored/check`, `.vendored/install` and the rest are installed copies of `templates/` and are vendor-protected here: they change only when git-vendored is installed into itself after a release. The sessions change `templates/` and `validate`, never the installed copies; this repository's own jobs must therefore work with the installed copies as they are today.
- The old workflows are vendor-protected (except `validate-vendor.yml`, which is this repository's own). The sessions do not add, change or delete a vendor-protected file; the planning session removes the old workflows from the integration branch after this unit.
- Coverage: the `test` job fails below 99% in total or for any shipped Python script (#125). Every change here comes with its tests; shell changes come with bats tests.
- Reaching vendors through the GitHub API instead of git (`gh api` in `templates/install`) is tracked separately and is not changed here.

## What ships

- `check` works as a git-cicd step and says what it looked at
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/check` (`get_branch_name`, lines 129-131; `main`, lines 231-260), `tests/`, `README.md`, `docs/`
  - shape: `check` takes the source branch from `CICD_SOURCE_BRANCH` when it is set, then `GITHUB_HEAD_REF`, then the current branch, so an install branch is let through under git-cicd in Actions and locally without a wrapper. With `--base`, when the working tree or the index holds changes that the commit range does not include, it says so in one line naming `--staged`, instead of only "No changed files". Nothing else about what is protected or allowed changes. The README documents running the check as a git-cicd job (`"steps": [".vendored/check"]`).

- An install refreshes a vendor's registry and manifest
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/install` (`save_vendor_config` line 120, `write_registry` line 111, `install_existing_vendor` line 871, the manifest handling), `tests/`, `README.md` (Vendor Contract, Manifest, Protection Rules)
  - shape: On every install of an existing vendor, the vendor's registry fields are replaced by what the installed version ships (the `_vendor` block of the config it installs or its template), and the manifest by what that install wrote, so `protected` and `allowed` are always those of the installed version. What the repository owns is kept: its config under `.vendored/configs/<vendor>.json` is not overwritten, and a field the repository has set for itself that the vendor contract says is the repository's (for example `private`) survives. The README states the rule and which registry fields a vendor owns. Tests cover an upgrade whose `allowed` list changed (the git-cicd case: `.github/workflows/git-cicd.yml` to `.github/workflows/git-cicd-*.yml`) and show that the check then accepts a regenerated workflow from an ordinary branch.

- An install pull request carries workflow files when its token may
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/install` (the `--pr` path, lines 1040-1125), `tests/`, `README.md` ("How Updates Work", authentication)
  - shape: In `--pr` mode, the files under `.github/workflows/` that an install wrote or removed are kept in the commit when the push is made with a token other than the workflow's own (a `VENDOR_PAT`), and left out as today otherwise. If the push is refused because the token may not write workflow files, the install does not fail without a pull request: it retries without the workflow files. Whenever workflow files were left out, the pull request's description lists them and says what to run and commit (for git-cicd, `.vendored/pkg/git-cicd/git-cicd generate`). The README says which permission the token needs. No token value is ever printed.

- The vendor argument is forgiving
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/install` (argument handling in `main`, the add path around lines 748-770), `tests/`
  - shape: Surrounding whitespace is trimmed from the vendor argument. `owner/repo` naming a repository that is already registered updates that vendor instead of failing with "already registered". The vendor, the version and the private flag can also be given through the environment (documented names), so a git-cicd job passes declared inputs without building a command line; arguments keep working. Error messages name what was wrong with the argument.

- git-vendored's own release, update and validate are git-cicd jobs
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `.vendored/configs/git-cicd.json`, `ci/` (new scripts, with bats tests), generated `.github/workflows/git-cicd-*.yml`, `.github/workflows/validate-vendor.yml` (removed), `README.md`, `AGENTS.md`, `docs/`
  - shape: The repository's config declares, beside `test` and `vendor-check`: (1) `release`: on `merge` for `main`, plus a manual run with `bump_type` (choices `patch`, `minor`, `major`; default `patch`), `subdirectory` and `changelog_description` as declared inputs; its step is `.vendored/pkg/git-semver/release` with no subcommand (git-semver v0.0.16 decides bump, publish or nothing itself and reads the `CICD_` variables and inputs). (2) `update-vendored`: on `cron` `0 9 * * 1` for `main`, plus a manual run with `vendor` (default `all`), `version` (default `latest`) and `private` as declared inputs; its step is a script under `ci/` that runs the installed `.vendored/install <vendor> --version <version> --pr --deps=install`, passing the inputs as arguments of an argv, never through a shell, with `GH_TOKEN` set to `VENDOR_PAT` when present, as `mangimangi/git-cicd`'s `ci/update-vendored.sh` does. (3) `validate`: manual only, with `repo` (required) and `version` (default `latest`) as declared inputs; its step is a script under `ci/` that runs this repository's own `validate`. `.vendored/pkg/git-cicd/git-cicd generate` is run and every generated workflow committed; `verify` passes. `validate-vendor.yml` is removed. `README.md` and `AGENTS.md` say how a release, an update and a validation are started here (Actions tab, **Manual**, the job name, the inputs as JSON).

## Acceptance criteria

- `templates/check` lets an install branch through with only `CICD_SOURCE_BRANCH` set, and with `--base` reports uncommitted or staged changes it did not read; tests show both.
- After an upgrade in a test repository, the registry's `allowed` and `protected` are those of the installed version, the repository's own config is untouched, and the check accepts a regenerated workflow committed from an ordinary branch.
- In `--pr` mode with a token that is not the workflow's own, the install commit contains the workflow files the install wrote; with the workflow's own token it does not, and the pull request description lists them with the command to run. A refused workflow push still ends with a pull request.
- `.vendored/install " owner/repo "` and `.vendored/install owner/repo` for a registered vendor both update it; the environment form works; tests show each.
- `.vendored/pkg/git-cicd/git-cicd validate` reports `test`, `vendor-check`, `release`, `update-vendored` and `validate`; `verify` passes; `.vendored/pkg/git-cicd/git-cicd check --setup` passes with coverage at 99% or more for every shipped Python script.
- The pull request into `plan/git-dev-883c` has a passing `Verdict / git-cicd:verdict`.
- `install.sh` still installs `check-vendor.yml` and `install-vendored.yml` into a consumer.
- `python3 .vendored/check --base origin/plan/git-dev-883c` reports nothing.

## Out of scope

- Deleting `version-bump.yml`, `check-vendor.yml`, `install-vendored.yml`, `dogfood.yml` or the git-dogfood pieces here (vendor-protected; done by the planning session).
- What `install.sh` installs into consumers; migrating any consumer.
- git-cicd's `install.sh` listing generated workflows in its manifest (an issue in git-cicd).
- Replacing `gh api` reads of a vendor with git; a platform adapter for pull requests.
- How a release gets past a protected `main` (the bump pull request opened with the workflow's token gets no checks): a question with the owner.
- Known-bad versions, `latest`, subscriptions, or anything else about how versions move.
