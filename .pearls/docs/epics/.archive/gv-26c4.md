# git-vendored: a vendor is installed through git, not the GitHub API

> Unit 5 of plan `git-dev-aef7` (record: `mangimangi/git-dev`, `.pearls/docs/epics/git-dev-aef7.md`). Agreed with the owner on 2026-11-28. Delivers into `plan/git-dev-aef7`, on top of unit 3 of the plan (the installer reads `CICD_WRITE_TOKEN` and `CICD_READ_TOKEN`, with `VENDOR_PAT` as the deprecated fallback). The line numbers below were read at v0.0.31, before unit 3; find each function by name and re-check before use.

## Problem

The owner, 2026-11-28: "generally for this git toolkit we want to build around *git* not github...it should theoretically be portable to a different platform or self hosted solution with minimal effort".

git-vendored reaches a vendor through the GitHub API for things git does itself on any host (`headaches/git-vendored-install-reaches-vendors-through-the-github-api-not-git.md`):

| What | Where | Today |
|---|---|---|
| Does the vendor exist | `templates/install` `check_repo_exists` line 228 | `gh api repos/{repo}` |
| Does it have an installer | `check_install_sh` line 241 | `gh api repos/{repo}/contents/install.sh` |
| Which version is the latest | `_resolve_from_releases` line 279, `_resolve_from_version_file` line 291 | `gh api .../releases/latest`, then `.../contents/VERSION` |
| Its dependencies, schema and installer at a version | `download_deps` line 373, `download_schema` line 393, `download_and_run_install` line 595 | `gh api .../contents/<file>?ref=` |
| The files an installer copies | `templates/lib/vendor-helpers.sh` `_vendor_download` line 30, `fetch_file` line 75, `fetch_dir` line 101 | `gh api .../contents/...`, falling back to `curl` on `raw.githubusercontent.com` |
| The bootstrap | `install.sh` lines 34-44 | the same two |
| Validating a vendor | `validate` lines 87-161 | six `gh api` calls of the same kinds |

Only two calls are platform work git cannot do: `gh pr create` (line 1419) and `gh pr merge --auto` (line 1443). They stay.

Consequences today: a vendor on another git host cannot be installed; every file is a separate API call (rate limits, and a token even for reads that git could do anonymously); the version that gets installed is whatever a platform's "latest release" says, with no commit recorded.

## What ships

One epic in git-vendored, refined into these.

- A vendor is fetched once, with git, at the version being installed — **gv-26c4.2**
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/install` (`check_repo_exists`, `check_install_sh`, `download_deps`, `download_schema`, `download_and_run_install`), `tests/`
  - shape: For an install, the vendor repository is fetched once at the tag of the version (a shallow fetch of that one ref into a temporary directory outside the repository, removed afterwards), and the installer, `deps.json` and the schema are read from that checkout. A vendor is named by a URL git can fetch; the existing `owner/repo` form keeps working and means the same repository on github.com. A private vendor is fetched with the read token given to git for that fetch only, never written to a config file or printed. A vendor that does not exist, a version with no tag, and a vendor with no installer are each reported as such. No `gh api` call remains on this path.

- "Latest" and the version list come from the vendor's tags — **gv-26c4.1**
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/install` (`resolve_version` line 256, `_resolve_from_releases`, `_resolve_from_version_file`), `tests/`, `README.md`
  - shape: The versions of a vendor are its version tags as `git ls-remote --tags` lists them, and "latest" is the highest of them by version order (tags that are not versions, such as `latest`, are ignored; a component's tags `<subdir>/vX.Y.Z` are a separate series). The commit each tag points at (the peeled commit of an annotated tag) is known from the same call and is recorded with the installed version in the vendor's manifest, so a later install or check can tell when a tag has moved. Resolution goes through one function, so that a later change (skipping a version marked defective; an override for a test) has one place to go.

- An installer's files come from the checkout — **gv-26c4.3**
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `templates/lib/vendor-helpers.sh` (`_vendor_download`, `fetch_file`, `fetch_dir`), `install.sh` (the bootstrap's download helper, lines 34-44), the vendor contract in `README.md` and `docs/`, `tests/` (bats)
  - shape: The framework tells an installer where the fetched vendor checkout is (a documented environment variable), and `fetch_file` and `fetch_dir` copy from it; a vendor's `install.sh` that uses the helpers needs no change. With no checkout given (an installer run by hand, an older framework) the helpers behave as today. An installer that downloads by itself keeps working. The bootstrap of git-vendored into a repository with nothing installed is documented with git (clone at a tag, run `install.sh`) as the primary way, and the `curl` one-liner as the GitHub-specific shortcut. The README's vendor contract says what a vendor must be (a git repository with version tags and an `install.sh` at its root) without naming a platform.

- `validate` checks a vendor with git — **gv-26c4.4**
  - vehicle: type: issue
  - source repo: git-vendored
  - target repo: git-vendored
  - affected surface: `validate` (lines 87-161), `tests/`
  - shape: `validate` uses the same fetch and the same tag listing as an install; it accepts a URL or `owner/repo`; its checks and messages are otherwise unchanged.

## Acceptance criteria

- With `gh` absent from `PATH`, a vendor is installed and upgraded from a local git repository used as the vendor (a `file://` URL) in the tests, and `validate` passes on it: no platform is involved until `--pr`.
- `grep` finds no `gh api` and no `raw.githubusercontent.com` on the install, resolve and validate paths; `gh pr create` and `gh pr merge` remain.
- The installed version's commit is recorded in the manifest; an install whose tag now points at another commit than the recorded one says so.
- An existing vendor (git-cicd, git-semver) installs and upgrades unchanged in a test repository; what lands on disk is byte-identical to an install by v0.0.31.
- Coverage stays at 99% or more for every shipped Python script; the bats tests cover the helpers' two modes.

## What already was decided (do not reopen)

- A pin is a version and a sha: the commit a version's tag points at is recorded with the installed version.
- Tokens: a private vendor is read with `CICD_READ_TOKEN`, then `CICD_WRITE_TOKEN`, then `VENDOR_PAT` (as unit 3 left it); a token is given to git for one command, never written to a config file and never printed.
- `gh pr create` and `gh pr merge --auto` stay; they are platform work.
- A vendor's own `install.sh` is not changed by this unit; an installer that uses the helpers must keep working without change, and so must one that downloads by itself.
- Coverage: the `test` job fails below 99% in total or for any shipped Python script; shell changes come with bats tests; no test reads a token from the environment or reaches the network (use local git repositories as vendors).
- This repository's own `.vendored/` files are installed copies and vendor-protected: change `templates/`, `install.sh` and `validate`, never the installed copies. Run `python3 .vendored/check --base origin/plan/git-dev-aef7` before finishing.
- The version on the integration branch is already higher than `main`'s (unit 3 raised it); raise it again only if this change is breaking for a vendor or an adopter, and say so in the changelog.

## Out of scope

- A platform adapter for pull requests and releases.
- Refusing or skipping versions marked defective; overrides for a test (leave the one resolution function they will need).
- Changing git-cicd's or git-semver's `install.sh`.
- The Python floor (a separate issue follows this unit).

## Refinement decisions

- **Commit stored in a new `.vendored/manifests/<vendor>.commit` file** (gv-26c4.1): `<vendor>.version` is read as a bare version by `get_current_version`, `--list`, `templates/check` and other tools, so its format stays unchanged. check protects the new file and remove deletes it.
- **Moved tag warns, does not refuse** (gv-26c4.1): the same-version install still skips unless `--force`. The criterion asks only that the install say so; refusing is outside this unit.
- **No fallback to a `VERSION` file on the default branch** (gv-26c4.1): an install always reads the vendor at a tag, so a version with no tag could never install, and the doc wants that case reported as such.
- **Version tags are `vX.Y.Z` or `X.Y.Z`, numeric order; `/`-containing tags ignored, resolver takes an optional tag prefix** (gv-26c4.1): this keeps component series separate and leaves one resolution function.
- **Explicit version tries `v<version>` then `<version>`** (gv-26c4.1): it keeps the retry order of `download_and_run_install` today.
- **Public vendors are read anonymously; the token goes through `GIT_CONFIG_COUNT`/`http.extraHeader` env for one command** (gv-26c4.1): the token never appears in argv, a URL, a config file or output, and git reads public repos without a token on any host.
- **`resolve_version` returns version, tag and commit (namedtuple)** (gv-26c4.1): one function gives the pin (version + sha).
- **Shallow `git clone --depth 1 --branch <tag>` into `tempfile.mkdtemp`, HEAD checked against the listed commit** (gv-26c4.2): one fetch per vendor, outside the repo, and the recorded sha is the one installed.
- **`check_install_sh` runs at the resolved tag, after resolution** (gv-26c4.2): what matters is that the version being installed has an installer.
- **Env var `VENDOR_CHECKOUT`; `VENDOR_REPO` keeps the configured string** (gv-26c4.2, gv-26c4.3): this follows the `VENDOR_*` contract, and installers that download by themselves keep working.
- **Vendor named by URL: name = last path component minus `.git`; config `repo` stores the target as given** (gv-26c4.2): `owner/repo` keeps its current meaning and naming.
- **Checkout-mode copy writes content only (no source mode), skips `.git`, symlinks and submodules** (gv-26c4.3): this matches today's download output byte for byte and mode for mode (the API mode handled only `file`/`dir`).
- **Byte-identical criterion checked by an automated mode-vs-mode test plus a manual git-cicd/git-semver diff against v0.0.31 recorded in the PR** (gv-26c4.3): tests may not reach the network.
- **README bootstrap example uses the current VERSION, not the stale 0.0.28** (gv-26c4.3): the example should install a current release.
- **`validate` imports `templates/install` via `SourceFileLoader` instead of duplicating code** (gv-26c4.4): the doc says "the same fetch and the same tag listing", and validate ships only next to `templates/install`.
- **validate sets `VENDOR_LIB` and `VENDOR_CHECKOUT` for the dry-run; check output order kept 1..8; version-resolvable detail reworded** (gv-26c4.4): helper-using vendors validate offline, and the old "no releases or VERSION file" message names a source that no longer exists.
- **validate keeps its token source (GH_TOKEN, then GITHUB_TOKEN)** (gv-26c4.4): the doc says validate's checks are otherwise unchanged.
- **No VERSION bump in any issue unless implementation finds a breaking change** (all): the integration branch is already above `main` (unit 3), and installers and tagged vendors keep working.
- **Planning-doc line numbers re-read on the current branch** (all): the doc's v0.0.31 numbers are replaced by current ones in each issue (for example `resolve_version` :282, `download_and_run_install` :621, vendor-helpers `_vendor_download` :32, validate :83-171).
